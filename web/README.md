# nanoinfer · live

The site for nanoinfer: a 23-chapter course on how a language model runs, and a lab where every engine stage runs in
your tab. GPT-2 124M runs in the browser through the real engine (`crates/core`, compiled to WebAssembly by
`crates/wasm`, plus the WebGPU stages from `crates/webgpu`). Every live figure is drawn from what the engine reports
while it runs: per-op timings, FLOPs, bytes, KV length, next-token probabilities and attention maps. None of it is a
mock-up.

## Run it

```sh
scripts/fetch_weights.sh          # once: HF gpt2 -> weights/gpt2 (gitignored)
node web/scripts/to-f16.mjs       # once: weights/gpt2/model-f16.safetensors (274 MB, what the page downloads)
cd web
npm install
npm run wasm                      # builds crates/wasm three ways -> src/engine/pkg, pkg-relaxed, pkg-threads
npm run dev                       # http://localhost:5199
node scripts/record.mjs           # optional: re-record public/recorded/ (the no-download fallback)
```

The page opens on **recorded** data (real engine output from `public/recorded/`, ~240 KB), so every figure draws
immediately. **Run live** downloads GPT-2 once (f16, 274 MB; `?weights=f32` for the 548 MB original), caches it in
OPFS, and from then on every figure is driven by the engine in your tab. In local dev the weights are served from
`../weights/gpt2` by a small Vite middleware, which also serves `../bench/results.jsonl` at `/bench/results.jsonl`
(production falls back to the snapshot in `public/recorded/native.jsonl`).

Toolchain: Rust with the `wasm32-unknown-unknown` target, and `cargo install wasm-bindgen-cli --version 0.2.129` (the
version must match the `wasm-bindgen` pin in `crates/wasm/Cargo.toml`). The threads build needs
`rustup toolchain install nightly --component rust-src` and is skipped without it. `wasm-opt` is used if on PATH.

URL knobs: `?build=simd128|relaxed|threads` forces a build (default: the best this browser validates), `?threads=N`
sizes the threads build's worker pool (default: all cores), `?weights=f32`.

Env overrides: `VITE_WEIGHTS_BASE` (where the page fetches `model.safetensors`, `vocab.json` and `merges.txt`),
`VITE_BENCH_URL` (results.jsonl), and `NANOINFER_WEIGHTS` (the directory the dev server serves).

## Site structure (see IA.md)

- `/` landing: the question, one live demo, the map of the course (`src/site/`)
- `/learn/<chapter>` the course: 23 chapters in 4 parts (part 0, "inference for systems engineers", is the recommended
  start), one idea and one primary figure each, ending with 2–3 check-yourself questions (`src/learn/`; the list is
  `src/learn/chapters.tsx`, part 0 in `src/learn/ch/p0/`, questions in `src/learn/checks.ts`, shared figure kit in
  `src/learn/kit.tsx`, the part-3 climb chart in `src/learn/Climb.tsx`). Visual language: `DESIGN.md`.
- `/learn/field-guide` the reference: constraint map + 53 terms (`src/learn/FieldGuide.tsx`, `src/learn/guide/`).
  Small precomputed data (real GPT-2 rows, a weight block, bench/batching.json, serving.json, specdec.json, webgpu.json and the headline
  numbers from results.jsonl) lives in
  `public/learn/data.json`, regenerated by `nice -n 10 python3 -I scripts/learn-data.py`.
- `/lab` the lab: every engine stage running in your tab, one figure per panel (`App.tsx`, `src/panels/registry.tsx`)

Routing is a ten-line pushState router (`src/learn/router.ts`); `vercel.json` rewrites every non-`/api` path to
`index.html` and sets the isolation headers.

## Select-to-ask

Select text anywhere → Ask, Explain, Define, Simplify ¶ or ✦ Deeper (or hold the mic and talk) → a streamed answer in a
side panel, with the surrounding `[data-ask-section]` text as context (`src/ask/`). The panel says which model wrote the
answer, who pays for it, and that it can be wrong. The browser calls `/api/ask`; the key never leaves the
server. `server/ask.ts` is a web-standard handler used by a Vite middleware in dev and by `api/ask.ts` (Vercel edge
function) in production. It proxies Together's OpenAI-compatible API (like Tangent), tries
`deepseek-ai/DeepSeek-V4.1-Flash-1017` first and falls back to `deepseek-ai/DeepSeek-V4.1-Flash` while Together doesn't
serve the new one, and rate-limits per IP (12/min, 60/hour, in memory).

Env (server side only): `TOGETHER_API_KEY` (required; put it in `web/.env.local`, gitignored, or the Vercel project env),
`NANOINFER_ASK_MODEL` (comma-separated preference list), `NANOINFER_ASK_BASE_URL`, `NANOINFER_ASK_KEY` (another
provider's key), `NANOINFER_ASK_RATE_LIMIT=off`. Without a key, the production build hides the selection toolbar
entirely (`useAskAvailable()` in `src/ask/AskLayer.tsx` is false, for any "select text to ask" hint); in `npm run dev`
the toolbar still appears and the panel says which variable to set.

## Architecture

```
crates/wasm  (standalone crate, own [workspace]; path dep on ../core)
  Engine      weights + tokenizer + N sessions ("slots"), each on any stage
  forward()   one real forward pass -> packed Float64Array trace
  stages()    Stage::ALL from core (new stages appear automatically), each with
              a wasmNote saying what it really runs here, + browser-only rungs
  simd.rs     browser rungs: wasm-simd (simd128, 4x4 tile), wasm-fma
              (relaxed-SIMD FMA), wasm-threads (wasm-bindgen-rayon), all on
              core's kv_cache::forward via the Kernels trait
  attention_maps()  analysis pass: all 144 heads' T×T matrices, via core's blocks
  logit_lens()      ln_f + LM head on the residual stream after every layer
  residual_stream() the token's 768-d vector after embed and each block
  logits()          a slot's full last logits (re-sampling in JS)
  Bytes::from_f16   streams an f16 safetensors in, widening to f32 as it goes
  bench_bandwidth / bench_peak_gflops   the two roofs, measured in-tab
  build.sh    pkg (simd128), pkg-relaxed, pkg-threads (nightly, shared memory)

web/scripts
  record.mjs  runs the relaxed wasm in Node, writes public/recorded/*
  to-f16.mjs  model.safetensors -> model-f16.safetensors

web/src/engine
  worker.ts   owns the wasm. Streams the checkpoint into wasm memory chunk by
              chunk (never held twice in JS), caches files in OPFS, decodes traces
  client.ts   typed RPC to the worker + one tiny store (useSyncExternalStore)
              that every panel reads, plus the vocab for decoding tokens
  generate.ts the generation loop (main thread: one RPC per token, so it's
              trivially cancellable) and the fixed-shape Ladder benchmark
web/src/lib/recorded.ts  loads + unpacks the recording into the same types
                         the live engine produces (Run, ForwardTrace, ...)
web/src/panels   one file per figure; registry.tsx is the page order
web/src/ui       Figure frame (per-figure provenance + "run live" button), theme
```

- **Recorded, then live.** At boot the store is filled from the recording (`source: "recorded"`); the run, config and
  roofs are the recorded ones and token text decodes from a vocab subset. Each figure reports what it's drawing via
  `useFigureSource()`, and its frame shows "recorded on an M4 · run live in your tab" or "live · this tab · build".
  Once the engine loads, the hero re-runs and every shared figure switches; figures with their own data (lens,
  attention, walkthrough, races) recompute when they're on screen.
- **Roofs per backend.** A CPU (wasm) run is judged against the two wasm probes (`bench_bandwidth`,
  `bench_peak_gflops`); a WebGPU run against the GPU read bandwidth from `webgpu_probe` (measured once, after the first
  live GPU run; the recorded probe in `webgpu.json` until then), with no compute roof. Bytes per token follow the
  stage's weight and LM-head formats and its KV width (`src/lib/roofs.ts`), so the speed-limit gauge (fig 5), the
  roofline (fig 6) and the ladder's hover all compare like with like.

- **One engine, one run.** The hero (fig 1) writes the shared `run` (tokens + every forward's trace). The time strip,
  byte budget, roofline and attention panels all redraw from that same run. Panels that need the engine to themselves
  (the KV race, the Ladder benchmark) open their own session slots and `claim()` the engine so runs don't interleave.
- **Packed trace.** Each `forward()` returns a header, then top-k, then an optional attention row, then 10 f64s per op
  (`kind, name, layer, d0, d1, d2, flops, bytes, start_ms, dur_ms`). Names and kinds are interned in grow-only tables, so
  new op kinds from future stages decode without code changes. Layout constants come from `trace_layout()`.
- **Timing.** `performance.now()` in the worker. The dev server sends COOP/COEP, so the page is cross-origin isolated
  and the timer resolution is ~5 µs (~100 µs otherwise). The page shows which one it got.
- **Isolation headers.** COOP `same-origin` and COEP `require-corp`, set on every response. They're needed for
  the threads build (SharedArrayBuffer). jkmr would need them site-wide (see research/03 §3.6).
- **Theme.** `src/styles.css` copies jkmr's `.minimal` tokens (`--m-bg`, `--m-accent`, `--m-heat-0..4`, ...). Canvas and
  SVG figures read them through `usePalette()`, which re-reads when `data-theme` changes on the `.minimal` host. The theme
  toggle uses jkmr's localStorage key.
- **Reduced motion.** All animation and transitions are disabled under `prefers-reduced-motion`, and the token stream
  doesn't use the blur-in effect.

## Adding a panel

1. Create `src/panels/MyPanel.tsx` exporting a default component. Read shared state with
   `useEngine((s) => s.run)` (or `s.config`, `s.bandwidthGBs`, `s.stages`, ...). Render `<NeedsEngine>` until the data you
   need exists.
2. If it has to drive the engine itself: `if (!claim("my-panel")) return;`, then `const slot = await engine.open(stage, maxSeq)`
   and `engine.forward(slot, tokens)` / `engine.sample(...)`. Finish with `engine.close(slot)` and `release("my-panel")`
   in a `finally`.
3. Add an entry to `PANELS` in `src/panels/registry.tsx` with `id`, `title`, a 1–3 sentence learner `caption`, and
   optional `intro` prose. Numbering and the frame are automatic.
4. Colours: use `usePalette()` and `kindColor(pal, op.kind)`, so the figure follows the theme and matches the others.
   Measure width with `useWidth()` (a callback ref, so it works for elements that mount late).

## Embedding in jkmr

The panels only depend on React, `src/engine/*`, `src/ui/*` and `src/lib/*`, plus the CSS in `src/styles.css` (scoped to
`.minimal`, with an `nv-` prefix). Plan: vendor the built `pkg/` and these folders into jkmr, register panels behind
`live <id>` fenced blocks in `toSegments` (research/03 §6), and lazy-load the engine so the home page bundle is unchanged.

## Weights: now and later

- **Now (local dev):** `model-f16.safetensors` (274 MB, `scripts/to-f16.mjs`), widened to f32 inside wasm while it
  streams (max |Δlogit| ~0.04 vs f32, greedy identical), or the raw f32 file with `?weights=f32`. Either way core
  parses and transposes f32 (`Model::from_safetensors`). The wasm heap peaks at about 1.05 GB during load. Files are cached in
  OPFS and written while they download. A ".ok" marker means a file was written completely. On the next visit the page
  loads from the cache automatically (it never auto-downloads).
- **Later (production):** pre-transposed f16 or Q8_0 shards of 16–32 MB with a `manifest.json` (sha256, offsets), hosted
  on the HF Hub. Use whole-shard GETs, because Range requests fail CORS on the Xet hop. That needs a core loader for
  packed shards (see `NEEDS_FROM_CORE.md`). Never ship f32 over the wire.

## Known issues

- WebGPU rungs run in Chrome (no `subgroups` there, so `webgpu-subgroup` is native-only); their recorded browser speeds
  are `public/recorded/webgpu.json`, made in the page with `__nanoinfer.webgpu().then(m => m.recordWebgpu())`.
- Core's own multithreaded stages (threads, spin-pool, fast-ops, quantised) run single-threaded in
  wasm (they start OS threads); the browser's threaded rung is `wasm-threads`.
- `wasm-threads` speeds up prefill ~2× over wasm-fma but not decode (fork/join cost per small matmul).
- The live stage race time-slices one engine thread, so its clock runs slower than real time until the slow lanes
  finish (the page says so); the recorded race plays at true speed.
- The CPU recording (`meta.json`, `run.json`, `bench.json`, `attention.bin`) was re-made on 19 Oct at 02:00 with
  nothing else benchmarking (1-min load 1.9 at the start, 3.0 at the end; a screen-sharing video encoder was running),
  from the engine at `6b77446`, Node 25.5 / V8 14.1, relaxed build, best of 4 interleaved rounds per stage. Against the
  18 Oct shared-machine recording: roofs 59 → 71 GB/s and 97 → 110 GFLOP/s; f32 rungs ~94–104 → 111–119 tok/s; and it
  now covers all 22 stages (it had 13). Its timings feed the landing hero's replay speed, chapter 8's loop timeline, and
  in the lab, until the reader goes live: figs 1, 2, 5, 6, 7 and the ladder's dashed browser bars. The WebGPU
  recording (`webgpu.json`, 18 Oct) was made with nothing else benchmarking.
- **Quantised stages in wasm** (re-recorded 19 Oct, 02:35, after core got a simd128 int8 dot and f16 widening,
  `docs/LOG.md` "Browser stage 4"): q8-rescore / q4-rescore / -attn decode at ~194 tok/s, kv16 / q8-prefill at ~162,
  q8 / q4 / -fast at ~97 (capped by their f16 LM head), f16 at 42, against 122–130 for the f32 rungs. Before the fix
  the same stages were 26–36 tok/s (scalar int8 dot). Same conditions as above (load 2.0, screen-sharing encoder
  running), roofs 71.6 GB/s / 108 GFLOP/s.
- Some browsers' storage quota is too small to cache 548 MB (incognito-like profiles cap OPFS at about 64 MB). The page
  still works there; it just downloads again next time.
- The first bandwidth probe right after loading reads about 40% low, so the page takes the best of two probes. It's still
  noisy (48–62 GB/s on an M4) and can move when other processes compete for memory bandwidth.
- `neon` and `tiled` have no NEON on wasm; the engine reports that per stage (`wasmNote`) and the page marks them *.
